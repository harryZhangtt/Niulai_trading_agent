# Progress and recovery

Compare the current state with the last verified progress: a validated artifact,
resolved uncertainty, completed check, or newly isolated failure. Narration,
rewritten plans, and repeated retrieval of unchanged material do not establish
progress. A long-running operation with observable forward movement is not a loop.

Classify the obstacle from observed evidence: transient tool failure, permanent
tool limitation, missing input/permission, flawed approach, oversized task, or
unfinished execution. Do not label difficult reasoning as an external dependency.

Choose a bounded next action: retry a plausibly transient failure, change an
assumption or input, use an authorized alternative, isolate a smaller subproblem,
or resume from verified state. Repetition needs a stated reason; unchanged hard
failures need a different approach. Preserve the original acceptance criteria:
an HTTP fallback working does not prove native search is repaired.

Set task-appropriate time/token/attempt limits using available measurements.
If telemetry is unavailable, label estimates; do not fabricate usage. On budget
exhaustion checkpoint and report incomplete work, not a false external blocker.

Before reporting blocked, record dependency, observed error, alternatives and
their outcomes, independent work remaining, and the smallest needed external
change. Continue independent authorized work. Respect real access boundaries;
never fabricate credentials, data, successful checks, or an excuse to stop.

Output: diagnosis, last progress evidence, selected recovery and budget, or an
evidenced escalation. Verify recovery against the requested outcome. This skill
does not itself schedule retries or monitor an agent outside its active turn.
