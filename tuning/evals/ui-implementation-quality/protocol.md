# UI implementation quality comparison v1

Freeze before solver dispatch. One independently authored synthetic existing-app
hardening task compares implementation outcomes, not advice or checklist wording.
The earlier routing screen did not establish skill effectiveness; the earlier
eight-test profile fixture was already inspected. This Dispatch Desk challenge
has new code, service behavior and failure inputs.

## Conditions and competing explanations

- Seed control: the unchanged supplied app. The author has verified normal
  operation and demonstrated its eleven hardening failures.
- General repair: the public task and common development-discipline guidance,
  without full UI skill packages. This is a capable-model engineering baseline.
- Routed repair: identical task, seed, tools, safety guidance and budget, plus
  compact UI policy/router and selectively loaded skill snapshots.
- Corrected control: author-created reference, excluded from both worker packets,
  validates that all outcome tests can pass on an implementation.

Hypothesis: selective UI guidance helps the worker discover and fix more actual
failure mechanisms without regressions. Rivals: generic engineering knowledge
already suffices; apparent benefit is one stochastic worker difference; a worker
optimizes prose without fixing behavior; additional guidance adds cost or harm.

Both workers inherit the same model/settings, have fresh contexts and receive
the same editable src/ surface and immutable service/view contracts. No model
overrides, external research, package installs, private data or production tools.
Each gets up to twelve minutes of implementation work and the same local
React/TypeScript/Vite/Playwright binaries. No grader feedback, semantic retries,
or selection of a best-of-many patch. A serialization-only repair may preserve
an otherwise finished response, with the failed artifact retained. Infrastructure
failure may be repaired only by changing a demonstrated environmental condition;
it does not silently become an implementation pass.

Workers write an initial inspection with concrete file/mechanism evidence before
editing, then implement and verify autonomously. The routed worker chooses a
route before reading full UI bodies and records declared loaded resources.
Baseline contains no UI bodies. Neither sees hidden tests, gold, reference,
other worker files, or prior responses. Filesystem restrictions are instructions,
not an OS-enforced sandbox: no secure-isolation claim. Shared host metadata and
model prior knowledge are not eliminated by withholding skill bodies.

## Frozen outcomes and gates

Twelve browser checks in gold.json cover normal behavior, extreme text/320px
overflow, late decoded success/failure, pending edits/entity switching, duplicate
activation, unknown committed writes, malformed data, sanitized rejection,
prop-driven/no-I/O preview and actual expensive-history rendering work. Preserve
all Q01–Q12 outcomes separately. They are dependent checks on ONE paired task,
not twelve independent samples. The author verified seed 1/12 and corrected
control 12/12 before solver dispatch; both typecheck and build. Freeze hashes
bind public task, seed, gold and tests.

Primary measurements: typecheck/build, per-case runtime outcome, preservation of
immutable contracts, and critical failures declared in gold. Discovery evidence
must name an actual seed mechanism and location; generic lists of possible bugs
do not establish autonomous detection. Compare initial inspection, final code,
worker verification and independent browser results. Do not reward verbosity,
file count, memoizing everything, a named state library or a preferred recovery
phrase. The preview is tested through its public interface with no service I/O;
render efficiency is measured by a supplied immutable expensive subtree probe.

A routed patch may support provisional use on this task only if it typechecks
and builds, preserves immutable files, passes all critical checks and has no
case regression against the general repair. A strictly higher pass count without
regressions is directional evidence; ties leave incremental benefit unproven.
Missing/infrastructure-invalid results are inconclusive, while observed criterion
violations are failures for that version. No averaging away data loss, duplicate
effects or leaked diagnostics with speed, aesthetics or lower token cost.

## Routing and cost

For this existing React hardening task, required packages are async-state-
reliability, impeccable, vercel-react-best-practices and playwright-cli. UIUX is
optional for a concrete layout/accessibility question; frontend-design and shadcn
are unnecessary without a new visual direction or component registry task.
Record misses, unnecessary loads and conditional references independently of
runtime quality. The same request and source are used in both arms.

Count serialized packet text, declared loaded skill/reference text and captured
response/source sizes using pinned tiktoken 0.12.0 o200k_base. Declared loads are
not an independently audited token trace. Provider usage, reasoning, tool framing,
cache effects and billing are unavailable. Report per-decision load and retained
session union where applicable. Cost cannot compensate for critical defects.

## Scope and stopping

Budget: one challenge author, two implementation workers, deterministic grading
and bounded evidence review. Do not tune the skill or grader on these outcomes
and relabel a rerun as fresh confirmation. Preserve every attempt and artifact.
Any later refinement requires a new run identity and fresh contrasting cases.
One task and one worker per arm cannot establish statistical/general superiority.

This is development evaluation source and isolated synthetic execution, not a
deployed application or major scheduler/provider/delivery runtime change. No
business job, credential, live provider or email is exercised by this benchmark.
Separate UI SessionStart configuration work retains its own actual-execution and
major-runtime acceptance status; these browser tests cannot accept that hook.
